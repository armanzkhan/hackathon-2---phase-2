# Data Model: Todo In-Memory Console Application

**Feature**: 001-todo-crud | **Date**: 2026-02-07

## Overview

This document defines the data structures and storage mechanisms for the Todo application. All data is stored in runtime memory only (no persistence) as required by the constitution.

## Domain Entities

### Todo Entity

**Purpose**: Represents a single task or item to be completed.

**Implementation**: Python dataclass with frozen=True for immutability.

**Fields**:

| Field | Type | Required | Default | Validation | Mutability |
|-------|------|----------|---------|------------|------------|
| id | int | Yes | (auto) | > 0, unique | Immutable |
| title | str | Yes | N/A | Non-empty after strip | Immutable |
| description | str | No | "" | None | Immutable |
| completed | bool | Yes | False | True or False only | Immutable |

**Field Details**:

#### id: int
- **Purpose**: Unique identifier for the todo
- **Assignment**: Auto-generated by repository (not user-provided)
- **Generation Strategy**: Simple counter starting at 1, incremented on each create
- **Uniqueness**: Guaranteed by repository's internal counter
- **Range**: Positive integers (1, 2, 3, ...)
- **Reuse**: IDs never reused, even after deletion
- **Immutability**: Cannot be changed after assignment

#### title: str
- **Purpose**: Brief description of the task
- **Required**: Yes (cannot be empty)
- **Validation**: Must not be empty after `strip()` (no whitespace-only titles)
- **Max Length**: No enforced limit (reasonable length assumed)
- **Validation Location**: Performed in `Todo.__post_init__` method
- **Error Handling**: Raises `ValueError` if validation fails
- **Example Valid**: "Buy groceries", "Call dentist", "Finish project report"
- **Example Invalid**: "", "   ", "\t\n"

#### description: str
- **Purpose**: Optional detailed information about the task
- **Required**: No (default: empty string)
- **Validation**: None (any string accepted, including empty)
- **Max Length**: No enforced limit (thousands of characters supported)
- **Default**: "" (empty string if not provided)
- **Example**: "Milk, eggs, bread, chips", "Schedule appointment for next Tuesday"

#### completed: bool
- **Purpose**: Indicates whether the task is finished
- **Required**: Yes (must be True or False)
- **Default**: False (new todos start as incomplete)
- **Mutation**: Only changed via `mark_complete()` method
- **Display**: Rendered as ✔ (True) or ✘ (False) in CLI

**Example Instances**:

```python
# Minimal todo (title only)
Todo(id=1, title="Buy groceries", description="", completed=False)

# Complete todo
Todo(id=2, title="Call dentist", description="Schedule checkup", completed=False)

# Completed todo
Todo(id=3, title="Finish report", description="Q4 summary", completed=True)
```

## Storage Schema

### Repository Internal Storage

**Structure**: Dictionary mapping ID to Todo instance

```python
class TodoRepository:
    _storage: dict[int, Todo]  # ID -> Todo mapping
    _next_id: int              # Counter for next ID
```

**Storage Characteristics**:
- **Type**: Python `dict[int, Todo]`
- **Key**: Todo ID (integer)
- **Value**: Todo instance (immutable dataclass)
- **Capacity**: Limited only by available memory
- **Ordering**: Unordered (sorted when retrieved via `get_all()`)
- **Thread Safety**: Not required (single-threaded application)

**ID Generation**:
- **Initial Value**: 1 (first todo gets ID 1)
- **Increment**: +1 for each new todo
- **Persistence**: Counter reset on application restart (expected behavior)
- **Collision Handling**: Not needed (simple counter guarantees uniqueness)

**Example Storage State**:

```python
# After creating 3 todos
{
    1: Todo(id=1, title="Buy groceries", description="", completed=False),
    2: Todo(id=2, title="Call dentist", description="Schedule checkup", completed=True),
    3: Todo(id=3, title="Finish report", description="", completed=False)
}
_next_id = 4  # Next todo will get ID 4
```

## Data Flow Diagrams

### Create Operation Flow

```
User Input (title, description)
    ↓
CLI Command Handler (validate input)
    ↓
Repository.create()
    ↓
Generate ID (_next_id++)
    ↓
Create Todo instance (validation in __post_init__)
    ↓
Store in _storage[id] = todo
    ↓
Return Todo instance
    ↓
CLI Display (format and show confirmation)
```

### Read Operation Flow

```
User Input (none for list, ID for single)
    ↓
CLI Command Handler
    ↓
Repository.get_all() or Repository.get_by_id(id)
    ↓
Retrieve from _storage
    ↓
Return list[Todo] or Todo | None
    ↓
CLI Display (format and show table/details)
```

### Update Operation Flow

```
User Input (ID, new_title, new_description)
    ↓
CLI Command Handler (validate input)
    ↓
Repository.update(id, title, description)
    ↓
Check if ID exists in _storage
    ↓
Get existing Todo
    ↓
Create new Todo with updated fields (preserve completed status)
    ↓
Replace in _storage[id] = updated_todo
    ↓
Return updated Todo
    ↓
CLI Display (show confirmation)
```

### Delete Operation Flow

```
User Input (ID)
    ↓
CLI Command Handler (validate ID format)
    ↓
Repository.delete(id)
    ↓
Check if ID exists in _storage
    ↓
Remove from _storage via del _storage[id]
    ↓
Return True (success) or False (not found)
    ↓
CLI Display (show confirmation or error)
```

### Mark Complete Operation Flow

```
User Input (ID)
    ↓
CLI Command Handler (validate ID format)
    ↓
Repository.mark_complete(id)
    ↓
Check if ID exists in _storage
    ↓
Get existing Todo
    ↓
Create new Todo with completed=True (preserve other fields)
    ↓
Replace in _storage[id] = updated_todo
    ↓
Return updated Todo
    ↓
CLI Display (show confirmation)
```

## Validation Rules

### Title Validation

**Rule**: Title must be non-empty after stripping whitespace.

**Implementation**:
```python
def validate_title(title: str) -> tuple[bool, str]:
    stripped = title.strip()
    if not stripped:
        return (False, "Title cannot be empty")
    return (True, "")
```

**Test Cases**:
- ✅ Valid: "Buy groceries", "A", "  Task with spaces  "
- ❌ Invalid: "", "   ", "\t", "\n\n"

### ID Validation

**Rule**: ID must be a valid positive integer.

**Implementation**:
```python
def validate_id(id_str: str) -> tuple[bool, int, str]:
    try:
        todo_id = int(id_str)
        if todo_id <= 0:
            return (False, 0, "ID must be positive")
        return (True, todo_id, "")
    except ValueError:
        return (False, 0, "Invalid ID format. Please enter a number.")
```

**Test Cases**:
- ✅ Valid: "1", "42", "999"
- ❌ Invalid: "abc", "1.5", "-1", "0", ""

### Description Validation

**Rule**: No validation (any string accepted).

**Implementation**:
```python
def validate_description(description: str) -> tuple[bool, str]:
    return (True, "")  # Always valid
```

**Test Cases**:
- ✅ Valid: Any string including "", "   ", very long strings

## Immutability Strategy

**Why Immutable?**
- Prevents accidental state mutation
- Makes testing easier (no hidden side effects)
- Simplifies reasoning about data flow
- Aligns with functional programming principles

**Implementation**:
- Use `@dataclass(frozen=True)` decorator
- All fields are read-only after creation
- Update operations return NEW Todo instances (replace pattern)

**Update Pattern Example**:
```python
# Getting existing todo
old_todo = repository.get_by_id(1)  # Todo(id=1, title="Old", ...)

# Update creates NEW instance
new_todo = repository.update(1, title="New Title")  # Todo(id=1, title="New", ...)

# old_todo is unchanged (immutable)
# repository storage now has new_todo at ID 1
```

## Performance Characteristics

### Operation Complexity

| Operation | Time Complexity | Space Complexity | Notes |
|-----------|-----------------|------------------|-------|
| Create | O(1) | O(1) | Direct dict insert |
| Get by ID | O(1) | O(1) | Direct dict lookup |
| Get All | O(n log n) | O(n) | Sort by ID before return |
| Update | O(1) | O(1) | Dict lookup + replace |
| Delete | O(1) | O(1) | Direct dict delete |
| Mark Complete | O(1) | O(1) | Dict lookup + replace |
| Exists Check | O(1) | O(1) | Dict membership test |

**Where**:
- n = number of todos in storage
- All operations are in-memory (no I/O overhead)

### Memory Usage

**Per Todo**:
- id: 28 bytes (Python int object)
- title: 50-100 bytes (varies with string length)
- description: 50-500 bytes (varies with string length)
- completed: 28 bytes (Python bool object)
- **Total**: ~150-650 bytes per todo (average ~300 bytes)

**Repository Overhead**:
- dict structure: ~240 bytes + 8 bytes per entry
- _next_id: 28 bytes
- **Total overhead**: ~270 bytes

**Example Calculations**:
- 100 todos: ~30KB + 270 bytes ≈ 30KB
- 500 todos: ~150KB + 270 bytes ≈ 150KB
- 1000 todos: ~300KB + 270 bytes ≈ 300KB

**Conclusion**: Memory usage is negligible for personal task management scale (< 1MB for 1000+ todos).

## Edge Cases and Limits

### Maximum Todo Count
- **Limit**: No hard limit (constrained only by available memory)
- **Practical Limit**: 10,000+ todos (still < 3MB memory)
- **Constitution Requirement**: Designed for personal use (100-1000 todos expected)

### Maximum ID Value
- **Limit**: Python 3 integers have no maximum (arbitrary precision)
- **Practical Limit**: Could run for years without overflow
- **Edge Case**: If somehow reaching sys.maxsize, Python handles automatically

### Maximum Title/Description Length
- **Limit**: No enforced limit
- **Practical Limit**: Terminal width for display (~80 chars typical)
- **Handling**: Display formatting may truncate for readability (data preserved)

### Empty Storage
- **Handling**: `get_all()` returns empty list `[]`
- **Display**: Show friendly message "No todos found. Create one to get started!"

### Deleted IDs
- **Behavior**: IDs never reused after deletion
- **Example**: Delete ID 5, next created todo gets ID 6 (not 5)
- **Rationale**: Simpler implementation, no ID recycling complexity

## Data Lifecycle

### Creation Lifecycle
1. User provides title (and optional description)
2. CLI validates title is non-empty
3. Repository generates unique ID
4. Todo instance created with validated data
5. Todo stored in repository dictionary
6. User sees confirmation with assigned ID

### Read Lifecycle
1. User requests todo(s) by ID or all
2. Repository looks up in dictionary
3. Todo instance(s) returned (or None if not found)
4. CLI formats and displays data
5. No data modification

### Update Lifecycle
1. User provides ID and new values
2. CLI validates input
3. Repository looks up existing todo
4. New Todo instance created with updated fields
5. Old instance replaced in dictionary
6. New instance returned
7. User sees confirmation

### Deletion Lifecycle
1. User provides ID to delete
2. CLI validates ID format
3. Repository removes entry from dictionary
4. Memory automatically freed (Python GC)
5. ID never reused
6. User sees confirmation

### Application Lifecycle
- **Startup**: Empty repository created, no data loaded
- **Runtime**: All data in memory, no persistence
- **Shutdown**: All data discarded, no save operation
- **Next Startup**: Fresh empty repository (expected behavior per constitution)

## Summary

**Key Takeaways**:
- Todo entity is immutable dataclass with 4 fields
- Storage is simple dict (ID → Todo) with O(1) operations
- ID generation via simple counter (guaranteed unique)
- No persistence (data ephemeral by design)
- Memory efficient (< 1MB for 1000+ todos)
- Validation at creation ensures data integrity
- All operations are in-memory and fast
